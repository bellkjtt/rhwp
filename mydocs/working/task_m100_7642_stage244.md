# 저장 단 구성의 회귀와 둥근 괄호 전진폭

Issue: #7642

## 저장 컷 변경의 실제 회귀

Source235로 나머지 39개 원본을 전쪽 비교하던 중 9월 2022 HWP의
10·11쪽이 35.41750%, 63.27433%로 미달했다. 원본·독립 Print는 그대로다.
Source186 전체 23쪽은 최저 91.35857%, 해당 쪽은 98.68987%, 97.90019%였다.
같은 원본·PDF의 Source213 재출력도 해당 쪽이 98.68987%, 97.90019%다.
Source213과 Source224의 실제 10쪽 render-tree를 대조한 결과 저장 컷 변경
이후 첫 수식과 문항 시작이 달라졌다. 단순 기존 미달로 분류하거나 이관하지 않는다.

Source224는 현재 문단 전체가 물리적으로 들어가면 저장 단 컷을 무조건
무시했다. 현재 문단 자신의 줄이 그대로여도 앞에서 재발행한 줄 때문에
과거 컷이 낡을 수 있지만, 같은 저장 단의 구성이 유지된 경우에는 여유가
있다는 이유만으로 다음 단의 내용 소속을 지울 수 없다.

`measure_endnote_render_ink_fit`와
`reflowed_endnote_whole_paragraph_fits`가 같은 기존
`endnote_column_has_reissued_rows` 결과를 소비하도록 한다. 저장 컷이 유효하고
앞 줄이 재발행되지 않은 단은 컷을 보존한다. 재발행된 단은 같은 실제
수용 경로로 전체·앞 조각을 검증한다. 허용치·원본·쪽수 기대값은 바꾸지 않는다.
9월 회귀와 10월 원래 실패 입력을 함께 확인해야 한다. 진단은 ignored
`stage242-sep-before-cut-native`, `stage243-source235-sep-bad-review`,
`stage244-september-cut-bisect`에 보존한다.

## 괄호 폭의 독립 근거

24개 독립 입력의 크기·기준선·폭·높이·저장 줄을 비운 뒤 한컴 MCP 2020으로
저장·Print를 완료했다. 실제 제품은 11.0.0.9136, Print method 0,
`hancom2020_pdf_driver_one_up`이다. 저장 job은
`6b7ea26e-446f-481b-899b-69feb625ed90`, Print job은
`7fea7034-3a30-4a02-982b-88835406944e`이며 두 download는 exit 0이다.
진단 입력·명령·메트릭은 ignored `stage241-small-delimiter-diagnostic`,
산출 HWP/PDF는 `pdf/issue7642-small-delimiter-diagnostic`에 있다.
원본 `exam_math_8.hwp`나 그 독립 PDF의 대체물로 쓰지 않는다.

11pt `LEFT ( a _n RIGHT )`의 한컴 저장 폭은 1725HU, 즉 23px이며
현재 본체 폭 13px와 두 괄호의 정상 전진폭 375HU씩으로 설명된다.
현재 확장 슬롯은 임의의 384/1024em을 반올림해 각각 450HU로 만들고
전체 25px를 발행한다. 원본의 px 위치를 핀으로 고정하는 문제가 아니라
크기별 글꼴 전진폭의 생산자와 구분자 소비자가 서로 다른 문제다.
확장 둥근 괄호도 이미 독립 저장으로 확인한 `source_font_advance::paren`을
소비하도록 한다. 대괄호와 빈 구분자, 큰 괄호의 조립·수식 본체는 그대로다.

## 검증 범위와 현재 판정

공용 `target/pr-review`에서 한 번 빌드한 뒤 9월·10월 원본 HWP/HWPX,
괄호 진단·math8, 사회·과학 및 정상 대조군을 묶어서 비교한다.
재발행 여부는 실제 진단으로 확인하며 두 입력의 컷을 문서 ID로 분기하지 않는다.
현재 보정 후 Native/fresh WASM·확대 판독·정식 관계 회귀·최종 Rust/lint는
미검증이다. 작은 괄호의 채움 윤곽과 조건식 간격 차이도 여전히 직접 판독 대상이다.
