# Issue #7642 단계 703: HWP3 묶음의 자식 상대 위치 소비

## 관측과 독립 근거

- PR #7882의 merge SHA `86a3c88fc89de9a2306a10bdda9a31023f0e24a5`와 최신 fetch 기준 `upstream/devel` `b3eaf7b10b15a2d40810d42acdcf4de6c1ba026b`는 현재 브랜치에 이미 포함되어 있다. 추가 리베이스는 필요하지 않다.
- source `6f77a7121750e95556fb3ead7881534d3e3278a9`의 #1892 원본 Native 1쪽은 83.82851%다. 새 review PNG에서 두 수평 치수선이 같은 원점에서 시작하며 첫 화살표 방향도 기준과 다름을 직접 확인했다. 완료 판정이 아니다.
- 원본의 첫 두 선은 상대 위치 `(0, 216)`과 `(4899, 226)`이다. 독립 한컴 저장 HWPX는 HWPUNIT으로 `(0, 864)`와 `(19596, 904)`를 기록하고 실제 Print PDF는 두 선을 문구의 양옆에 표시한다. 중첩 묶음은 부모 `(1352, 0)`와 자식 `(0, 308)`을 한컴 저장본에서 `(1352, 308)`로 합성한다.
- 기존 HWP3 mapper는 상대 위치를 `offset_x/y`에만 보존했다. 그룹 렌더러는 자식의 `render_tx/ty`를 사용하므로 항상 identity인 자식 행렬에서 위치를 잃었다. 과거 자기정합 검사가 identity를 기대한 사실은 독립 출력의 위치 계약을 대체하지 않는다.

## 수정 경로와 반례

- HWP3 트리 구성 시 자식의 상대 위치를 최상위 묶음의 로컬 좌표로 누적한다. `offset_x/y`와 깊이는 보존한다. 최상위 페이지 위치는 기존 CommonObjAttr가 담당하므로 루트의 앵커를 중복 가산하지 않는다.
- `원본 상대 위치 → parser의 누적 render_tx/ty → 그룹 자식의 공통 배치 → 선 끝점/글상자 → SVG/paint`와 HWP/HWPX 왕복 저장이 같은 결과를 소비한다. HWP3 전용 렌더러 분기와 문서 ID 예외는 추가하지 않는다.
- 확인 대상은 서로 다른 원점의 형제, 부모 위치를 상속하는 중첩 자식, 루트의 페이지 앵커, 원본의 비가시 선이다. 회전/배율의 완전한 HWP3 변환 계약은 이번 이동 보정으로 입증하지 않는다.
- 독립 Print 기준의 전쪽 Native/fresh WASM 90% 이상과 확대 판독 전에 새 렌더링 회귀를 추가하거나 기존 기대값을 갱신하지 않는다. 이번 변경의 빌드·lint·시각 결과는 아직 미검증이다.
