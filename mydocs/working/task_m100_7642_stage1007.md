# 단계 1007 저장 쪽 경계의 실제 소유와 WMF 글꼴 이름 대조

Issue: #7642.

## 구현 전 원인 추적과 검증 계획

tracked visibility HWPX는 동일 원본과 독립 한컴 Print 6쪽에 대해 고정 base `a5e88ad682c805e1d845502ddc9521b94ea8eccd`는 6쪽, 현재 코드는 7쪽이다. 처음 다섯 쪽의 내용 분포는 같고 마지막 예산 표만 다음 쪽으로 밀렸다. 단계1003~1005의 실제 흐름 추적에서 6쪽은 재조판 문단93만 소비했는데, 문단94의 저장 되감김 판정은 이전 쪽의 문단92 저장 끝을 현재 흐름 끝과 대조했다. 숫자 일치가 같은 물리 쪽 소유를 입증하지 못한다.

공통 생산 경로는 저장 문단 끝 → `stored_rewind_boundary_matches_current_flow` → `stored_page_boundary_invalidated_by_reflow` 및 `whole_fit`의 덜 찬 쪽 경계 → 실제 쪽 분리다. 두 소비 지점에 현재 물리 frame의 `PageItem`을 전달하고, 저장 끝의 원본 소유 문단이 현재 frame에 포함될 때만 기존 위치 허용치를 적용한다. 명시적 쪽 나누기·충분히 찬 쪽의 기존 경계는 바꾸지 않는다. 같은 frame에서 저장 소유를 실제 소비한 정상 되감김은 유지해야 한다. 기존 #5169의 정확한 6쪽 검사를 바꾸지 않고 #6761·#7333·#6132 관련 경계 검사도 함께 실행한다. 부분 문단·표 소유는 기존 `PageItem`의 소유 인덱스를 사용하며, 단순 좌표 겹침으로 소유를 추측하지 않는다.

별도 WMF 경로에서는 본문이 쓰는 설치 글꼴 별칭을 SVG 그림만 누락했다. HWP3 sample16 18쪽의 그림 SVG는 `굴림체` 다음에 다른 family fallback을 넣지만, 실제 시스템의 해당 글꼴 family는 `GulimChe`다. 본문 renderer의 기존 설치 별칭 표를 WMF SVG 직렬화에서도 재사용한다. `LOGFONT` face → 원래 이름과 설치 별칭 → SVG font-family → Native/브라우저 glyph 선택 경로를 대조한다. 원래 이름·크기·굵기·문자열·그림 좌표와 일반 fallback 순서는 보존한다. 별칭이 없는 face는 그대로 둔다. 공개 WMF 재생 경로에 합성 글꼴 이름/문자 보존 계약을 추가하되 실물 시각 통과로 표현하지 않는다.

두 원인을 묶어 보정한 뒤 공유 target, 빌드 잡8로 한 번 빌드하고 관련 검사를 묶어서 확인한다. 이후 실제 원본의 전쪽 Native/fresh WASM TSV와 직접 확대 판독을 다시 수행한다. 새 실물 회귀 또는 기존 기대값 갱신은 전쪽 90% 이상 증거를 갖춘 뒤에만 처리한다. 최종 release WASM·전체 회귀·lint·base 하락 비교는 별도로 남아 있다.
