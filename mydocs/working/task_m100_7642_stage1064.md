# 단계 1064 HWP3 원본 글꼴 종류의 보존

Issue: #7642. 검증 전 source는 `bc66c8a88392550330fb45421e3061dc725c2b8c`다.

## 독립 근거

HWP3 sample16의 Native 19쪽은88.56619%다. 단순 획 두께 차이로 분류하기 전에 같은 글자의 실제 원점을 대조했다. 첫 줄 `내․외부`의 U+2024 뒤에서 약 반 글자 폭의 원점 차이가 생긴다. 원본의 기호 슬롯은 글꼴 번호1, 원래 이름 `신명조`다. 파서는 이를 `HY신명조`로 정규화하고 원래 이름을 alt_name에 보존하지만, 종류는 Font::default의 unknown(0)으로 남긴다. 따라서 공통 기호 폭 소비자가 원본 HFT 계약을 읽지 못한다.

독립 원본 Print(`pdf/issue7642-hwp3-original-print/hwp3-sample16-2020.pdf`, SHA-256 `f1f2e6dd265d098ea468bae14b44e98a1609dd7eba293f91d73ba16704be73c5`)에서 기호는 Type3로 출력되고 `․`는 전각이다. 같은 원본을 한컴에서 저장한 `samples/hwp3-sample16-hwp5.hwpx`의 대응 글자모양도 기호 슬롯을 `한양신명조`, type=HFT로 보존한다. RHWP 재저장 진단 파일은 원본 parser metadata를 읽는 용도로만 쓰며 독립 기준으로 사용하지 않는다.

## 수정 범위와 소비 경로

원래 HWP3 명칭을 이미 지원하던 legacy 정규화 분기에서 HFT 원본 종류도 함께 보존한다. 이름 치환 표와 표시 체인을 새로 추가하거나 바꾸지 않는다. 실제 TTF 명칭·정규화하지 않은 미확인 이름은 기존 unknown 분기를 유지한다. 새 글꼴 파일·윤곽선·특정 문서 조건을 넣지 않는다.

`HWP3 Font declaration → 공통 Font.alt_type → lookup_font_name_decision → 기호 슬롯 hft_fullwidth_dot → 공통 문자 폭·charX·줄 구성 → Native/WASM`을 대조한다. parser의 종류 보존이며 renderer에 HWP3 분기를 추가하지 않는다. 글꼴 공급·paint 이름과 메트릭 결정면을 혼합하지 않는다.

## 검증 계약

합성 원본의 legacy `신명조`와 정규화 없는 `바탕`을 대조해 이름 보존, 언어별 종류, 실제 공통 기호 소비자까지 검사한다. 실물 문서의 고정 좌표는 추가하지 않는다. 수정 전 실패/수정 후 통과와 같은 원본의64쪽 Native/fresh WASM·대표 review를 연결한다. 원본19쪽의 통과를 실행하기 전에는 실물 회귀를 추가하거나 기대값을 갱신하지 않는다.

## 수정 전 실행

초기 합성 글꼴명의 EUC-KR 바이트는 HWP3 원본 hchar 인코딩과 달라 이름 확인에서 먼저 실패했다. 이를 엔진 결함 재현으로 세지 않는다. 실제 원본에서 확인한 HWP3 hchar 바이트(신명조 `afa5a177b9a1`, 바탕 `a461c877`)로 정정한 실행은 이름 검사를 통과하고 원본 종류가 실제0/기대2라서 실패했다. `stage1064-corrected-fixture-tests.log`에 보존했다. 같은 실행에서 정정한 캡션 관계 검사는 통과했다.

구현은 기존 legacy 이름 정규화 분기에서 `Font.alt_type=2`를 보존하는3줄이며 새 이름 치환 규칙은 없다. 한컴 재저장본의 대응 HFT 종류와 독립 Print의 전각 리더를 함께 근거로 쓴다. 미확인 이름을 임의로 HFT로 분류하지 않는다.
